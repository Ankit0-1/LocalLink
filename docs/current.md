# Current State

## Database schema

All models use PostgreSQL native `uuid` primary/foreign keys (`@db.Uuid`, `dbgenerated("gen_random_uuid()")`), not `cuid()`. This was migrated in `use_uuid_identifiers` / `use_db_uuid_defaults`.

`DeliveryRequest.orderId` is `@unique` — each order may have exactly one delivery request, matching the "atomically creates the order's one delivery request" invariant in the README. This constraint was accidentally dropped when `use_uuid_identifiers` rebuilt the column as a plain (non-unique) index, and was restored by migration `20260716120000_restore_delivery_request_uniqueness`.

Verified 2026-07-17 by applying all 7 migrations to a throwaway Postgres 16 container: `prisma migrate deploy` succeeds, `prisma migrate diff` against the schema shows zero drift, and `prisma generate` succeeds.

Known minor issue (not fixed, pre-existing, low priority): `DeliveryRequest` carries both a `@unique` constraint and a separate `@@index([orderId])` on the same column — the plain index is redundant since the unique index already serves lookups.

## Authentication (Phase 1 — backend complete)

`POST /api/auth/register`, `POST /api/auth/login`, and `GET /api/auth/me` are implemented (`apps/api/src/routes/auth.ts`), backed by `requireAuth` / `requireRole` middleware (`apps/api/src/middleware/auth.ts`) and JWT helpers (`apps/api/src/lib/auth.ts`, 1-day expiry, `sub`/`role` claims).

The API CORS middleware (`apps/api/src/middleware/cors.ts`) allows the local Vite origins by default and responds to browser preflight requests. Deployments configure allowed UI origins through the comma-separated `CORS_ALLOWED_ORIGINS` environment variable.

All three endpoints now share a single response contract: `register` and `login` return `{ user, accessToken }`, `me` returns `{ user }` — and `user` is always the same field set (`safeUserSelect`: id, name, email, role, phone, profileImage, isActive, verificationStatus, createdAt) regardless of endpoint. Previously `login` returned `{ data, accessToken }` with extra fields (`verificationDocumentUrl`, `verificationNotes`, `updatedAt`) not present in the other two responses; this drift is fixed.

Debug/PII `console.log` calls that logged full user objects and error details in the auth routes have been removed.

JWT issuance/verification logic itself is unchanged.

Known gaps (tracked in `TASKS.md` Phase 1, not yet done):
- No admin-provisioning path exists (`ADMIN` can't self-register and there's no seed/admin-creation route).
- No rate limiting on `/login`.
- `requireRole` is not yet combined with ownership checks anywhere (no route uses it yet) — README explicitly calls out that ownership must be checked in the handler in addition to role.

## Vendor order fulfillment (Phase 5)

- `apps/api/src/routes/vendor.ts` — added, scoped to `store: { vendorId: req.user!.id }` throughout:
  - `GET /orders` — every order across all of the vendor's stores, most recent first, including customer (`id`, `name`, `phone`) and item/product summaries.
  - `PATCH /orders/:orderId/accept` — `PENDING` → `ACCEPTED`.
  - `PATCH /orders/:orderId/reject` — `PENDING` → `REJECTED`.
  - `PATCH /orders/:orderId/preparing` — `ACCEPTED` → `PREPARING`.
  - `PATCH /orders/:orderId/ready-for-pickup` — `PREPARING` → `READY_FOR_PICKUP`, and atomically creates the order's `DeliveryRequest` inside a `prisma.$transaction` (order status update + `deliveryRequest.create` together). Each transition handler first does an ownership-scoped lookup (404 if the order doesn't belong to this vendor) then checks the order is in the required prior status (409 otherwise) — so a vendor can never act on another vendor's order, and out-of-order transitions (e.g. `preparing` before `accept`) are rejected. The existing `orderId @unique` constraint on `DeliveryRequest` (see the Database schema section above) is the backstop against a duplicate delivery request under a race between two concurrent `ready-for-pickup` calls; the second one's `deliveryRequest.create` throws Prisma error `P2002`, which is caught and turned into a 409 rather than a 500.
- `apps/web/src/features/vendor/types.ts` — added `OrderItem`/`Order` (mirrors the vendor order response shape, including `customer`).
- `apps/web/src/features/vendor/api.ts` — added `listOrders`, `acceptOrder`, `rejectOrder`, `markOrderPreparing`, `markOrderReadyForPickup`, all thin `apiClient` wrappers.
- `apps/web/src/features/vendor/VendorDashboard.tsx` — added an "Orders" section (third column in the dashboard grid) listing every order across the vendor's stores with its status and total, and status-conditional action buttons (`PENDING` → Accept/Reject, `ACCEPTED` → Start preparing, `PREPARING` → Ready for pickup). Actions refetch the order list on success; failures surface the backend's `ApiError` message the same way the rest of the dashboard does.

Not in this slice: delivery-partner-facing endpoints/UI (Phase 6 — offering the `READY_FOR_PICKUP` job, first-eligible-acceptance assignment, pickup/delivery transitions) are still entirely unbuilt; the `DeliveryRequest` row this phase creates just sits at `PENDING` with no consumer yet.

## Delivery partner flow (Phase 6)

- `apps/api/src/routes/delivery.ts` — new router, `requireAuth, requireRole(Role.DELIVERY_PARTNER)` applied to the whole router, mounted at `/api/delivery` in `apps/api/src/server.ts`:
  - `GET /jobs` — every `DeliveryRequest` still `status: PENDING` (i.e. not yet claimed), oldest first, with the order's store/customer summary. Visible to every delivery partner — there's no per-partner offer/assignment queue yet, just "first to claim it wins."
  - `PATCH /jobs/:deliveryRequestId/accept` — the concurrency-safe claim. Inside one `prisma.$transaction`: a conditional `deliveryRequest.updateMany({ where: { id, status: PENDING, deliveryPartnerId: null }, data: { status: ACCEPTED, deliveryPartnerId } })` is the atomic compare-and-set — Postgres serializes concurrent `UPDATE`s against the same row via the row lock, so only the request that acquires the lock while the row is still `PENDING` updates it; every later concurrent request re-evaluates the `WHERE` clause against the now-`ACCEPTED` row and matches zero rows. `claimed.count === 0` (lost the race, or the job no longer exists/is already taken) → the transaction returns `null` and the route responds 409. On a win, the same transaction updates the `Order` (`deliveryPartnerId`, `status: DELIVERY_ACCEPTED`) so the delivery request and the order never disagree about who's assigned.
  - `GET /orders` — orders assigned to the current partner (`deliveryPartnerId: req.user!.id`), most recently updated first — covers accepted, picked-up, and delivered in one list.
  - `PATCH /orders/:orderId/picked-up` — `DELIVERY_ACCEPTED` → `PICKED_UP`, ownership-scoped via `findAssignedOrder` (looks up by `id` **and** `deliveryPartnerId` together, so an order assigned to someone else reads as a plain 404, matching the vendor routes' convention).
  - `PATCH /orders/:orderId/delivered` — `PICKED_UP` → `DELIVERED`, same ownership scoping.
  - `OrderStatus.SEARCHING_DELIVERY` (defined in the schema) is not used anywhere in this flow — the order sits at `READY_FOR_PICKUP` from the moment the vendor marks it ready (Phase 5) until a partner accepts, at which point it jumps straight to `DELIVERY_ACCEPTED`. Flagging this in case a later phase intends `SEARCHING_DELIVERY` to mean something distinct (e.g. "delivery request exists but no partner has looked yet") — as built, there's no state that maps to it.
- `apps/web/src/features/delivery/types.ts` — `Order` (store/customer summary shape returned by every delivery endpoint) and `Job` (wraps `Order` with the delivery request's own `id`/`status`/`createdAt`).
- `apps/web/src/features/delivery/api.ts` — `listJobs`, `acceptJob`, `listMyOrders`, `markPickedUp`, `markDelivered`; thin `apiClient` wrappers, same pattern as `features/vendor/api.ts`.
- `apps/web/src/features/delivery/DeliveryDashboard.tsx` — two-column layout matching `VendorDashboard`/`CustomerDashboard`'s style: "Available jobs" (Accept button per job) and "My deliveries" (status-conditional "Mark picked up"/"Mark delivered" buttons). Accepting refetches both lists (a lost race removes the job from "Available jobs" without a page reload) and shows the backend's `ApiError` message on a lost race rather than a generic failure.
- `apps/web/src/app/router.tsx` — added a `RequireRole allowedRoles={['DELIVERY_PARTNER']}` branch under the existing `RequireAuth` layout route, gating `/delivery` → `DeliveryDashboard` (mirrors how `/customer` and `/vendor` are already gated).

## Realtime updates (Phase 7)

- `apps/api/src/lib/socket.ts` — new module, `initSocketServer(httpServer)`, called once from `server.ts` against the same `http.Server` Express is attached to (switched `app.listen` to `createServer(app)` + `httpServer.listen` to share one port between HTTP and WebSocket traffic).
  - **Auth**: a Socket.IO `io.use` middleware requires `socket.handshake.auth.token`, verifies it with the same `verifyAccessToken` the HTTP `requireAuth` middleware uses, and re-checks the user is still active in the DB — a socket connection with no token, an expired/invalid token, or a deactivated account's token is rejected at the handshake (`connect_error`), never reaching `connection`.
  - **Room assignment is entirely server-side**: on `connection`, the socket joins `role:${role}` always, plus exactly one of `customer:${userId}` / `vendor:${userId}` / `deliveryPartner:${userId}` based on the *verified* JWT claims — the client has no way to request a different room. This is what makes the Definition of Done's "no realtime event delivered to an unauthorized client" true by construction rather than by a per-event check.
  - **Emit helpers**: `emitOrderUpdated(order)` sends to the customer's room, the vendor's room, the assigned delivery partner's room (if any), and the admin room. `emitJobOffered(job)` / `emitJobClaimed(job)` broadcast to every delivery partner (`role:DELIVERY_PARTNER`) plus admins, since job offers are first-eligible-acceptance rather than targeted at one partner.
  - No admin dashboard/UI consumes the `role:ADMIN` room yet (that's Phase 8) — the server-side broadcast to it is already correct and forward-compatible, there's just nothing listening client-side.
- Emit call sites (one `emitOrderUpdated` per state-changing mutation, so every dashboard's view of an order can never silently drift from the database):
  - `apps/api/src/routes/customer.ts`'s `POST /orders` (checkout) — added `vendorId` to the transaction's `store` select so the event payload has it, but `serializeOrder` was changed to build the client-facing `store` object explicitly (`{ id, name }`) rather than spreading the Prisma result, so `vendorId` is used for the socket payload only and never leaks into the HTTP response.
  - `apps/api/src/routes/vendor.ts`'s four transitions (`accept`/`reject`/`preparing`/`ready-for-pickup`) — `vendorId` comes straight from `req.user!.id` (no extra query needed, since `findOwnedOrder` already proved ownership). `ready-for-pickup` additionally captures the newly created `DeliveryRequest`'s id out of the transaction and calls `emitJobOffered`.
  - `apps/api/src/routes/delivery.ts`'s `accept`/`picked-up`/`delivered` — `jobOrderSelect`'s `store` select gained `vendorId` (same leak-prevention pattern as `customer.ts`: `serializeOrder` explicitly rebuilds `store` without it). `accept` emits both `emitOrderUpdated` (now-assigned order) and `emitJobClaimed` (so every other partner's dashboard drops the job without polling).
- `apps/web/src/lib/socket.ts` — thin wrapper: `connectSocket(token)` creates (replacing any existing) `socket.io-client` instance pointed at `env.apiUrl` with `auth: { token }`; `disconnectSocket()`; `getSocket()`.
- `apps/web/src/features/auth/AuthContext.tsx` — `connectSocket`/`disconnectSocket` calls were placed directly in `login()`, `register()`, the rehydration success callback, and `logout()` — deliberately *not* a separate `useEffect` watching `state.user`. Reasoning: React runs child effects before parent effects within a commit, so if connection were driven by an `AuthProvider`-level effect reacting to `state.user`, a freshly-mounted dashboard's own mount effect (which subscribes to socket events) could run *before* `AuthProvider`'s effect actually created the socket, leaving `getSocket()` `null` at subscribe time. Calling `connectSocket` synchronously, inline, before the `dispatch` that causes the dashboard to mount, guarantees the socket instance already exists by the time any dashboard effect runs.
- `apps/web/src/features/{customer/CustomerDashboard,vendor/VendorDashboard,delivery/DeliveryDashboard}.tsx` — each added a `useEffect` (mount/unmount only) that calls `getSocket()` and subscribes to the relevant event(s), calling the dashboard's existing refetch function on receipt: `CustomerDashboard` and `VendorDashboard` refetch orders on `order:updated`; `DeliveryDashboard` refetches orders on `order:updated` and refetches jobs on `delivery:job-offered`/`delivery:job-claimed`. No event payload filtering is needed client-side — room membership already guarantees every event a socket receives is relevant to it.

Verified against a real backend (throwaway `postgres:16-alpine` container + `prisma migrate deploy` + the actual `apps/api` server, socket server included): using real `socket.io-client` connections (not a mock) for a customer, an unrelated second customer, a vendor, and a delivery partner, drove one order through its full lifecycle (checkout → accept → preparing → ready-for-pickup → delivery-accept → picked-up → delivered) via HTTP calls while all four sockets listened. Confirmed: the order's own customer and its vendor each received all 7 `order:updated` events; the unrelated second customer received **zero** events of any kind; the delivery partner received exactly one `delivery:job-offered`, one `delivery:job-claimed` (its own), and `order:updated` only for the 3 transitions after it was assigned (not the 4 before); the final event every relevant party saw carried `status: "DELIVERED"`. Separately confirmed the auth handshake rejects both a missing token and a garbage token with `connect_error`, never reaching `connection`. Also confirmed `tsc --noEmit`, `eslint` (0 new errors — the pre-existing unrelated errors in `auth.ts`/`server.ts`/`customer/api.ts` are untouched), and `npm run build` pass for both `apps/api` and `apps/web`. All verification containers/servers were torn down afterward; nothing from this verification was committed.

## Automated testing + CI (Phase 9)

No test runner existed anywhere in the repo before this slice — every prior phase was verified manually (throwaway Postgres containers + `curl`/`socket.io-client` scripts, torn down after each session). This slice adds a real, permanent, CI-enforced test suite for both apps.

### Backend (`apps/api`)

- `apps/api/src/app.ts` — new. The `express()` app, middleware, and routes, previously all inline in `server.ts`, extracted so it can be imported and driven by `supertest` without opening a real port or starting the Socket.IO server. `server.ts` is now just `createServer(app)` + `initSocketServer` + `httpServer.listen`.
- `apps/api/src/lib/socket.ts` — `getIo()` no longer throws when `initSocketServer` hasn't run; the three `emit*` functions now no-op via `getIo()?.to(...)`. This wasn't just a testability shim: it's a real bug fix the test suite caught immediately — `orderLifecycle.test.ts`'s first run 500'd on checkout, because `app.ts` (by design) never calls `initSocketServer`, and the old `getIo()` threw. In production this same class of bug would have meant a checkout crashing if the socket server ever failed to initialize; emitting a live-update event should never be able to fail the request that triggered it.
- `apps/api/vitest.config.ts` + `apps/api/tests/globalSetup.ts` — `globalSetup` starts a throwaway `postgres:16-alpine` container via `@testcontainers/postgresql` once per test run, sets `DATABASE_URL`/`JWT_SECRET` on `process.env`, and runs `prisma migrate deploy` against it, all before any test file loads. `pool: 'forks'` + `fileParallelism: false` because every test file shares that one database. Requires only a working Docker daemon — no manually-managed test database, no docker-compose file, nothing to remember to start by hand.
- `apps/api/tests/helpers.ts` — `resetDatabase()` (`TRUNCATE ... CASCADE` across every app table, run in a `beforeEach` via `tests/setupEach.ts` so tests never leak state into each other) and `createUser(role, options)` (creates a user directly via Prisma with a low bcrypt cost for speed, signs a real token with the same `createAccessToken` the auth routes use).
- `apps/api/tests/authorization.test.ts` (11 tests) — every router rejects no-token (401) and a garbage token (401); wrong-role requests get 403; a deactivated user's still-valid-looking token gets 401; and ownership is enforced as 404-not-403 across vendor stores/products/orders, customer orders, and delivery-partner-assigned orders — matching the convention established since Phase 2 (an unowned resource looks identical to a nonexistent one).
- `apps/api/tests/orderLifecycle.test.ts` (2 tests) — drives one order through every status via real HTTP calls (register→store→product→cart→checkout→accept→preparing→ready-for-pickup→delivery-accept→picked-up→delivered), asserting the status at each step, that exactly one `DeliveryRequest` is created, that out-of-order transitions 409, and that the customer's tracking view reflects the final state. A second test confirms a rejected order can never move forward.
- `apps/api/tests/singleStoreCart.test.ts` (4 tests) — adding a second store's product while the cart holds a different store's item is rejected (409) and leaves the cart untouched; removing the blocking item allows the new store; checkout of an empty cart is rejected (400); the order total is computed server-side from current product prices regardless of what the client sends in the request body.
- `apps/api/tests/concurrentDelivery.test.ts` (2 tests) — fires 8 concurrent `PATCH .../accept` requests (via `Promise.all`, real parallel HTTP through the in-process app against the real Postgres container) at the same delivery job: exactly 1 succeeds, the other 7 get 409, and the database's `DeliveryRequest`/`Order` rows agree on the single winning partner. A second test confirms a already-claimed job rejects a later, non-concurrent second attempt too.
- 19 tests total, all passing; `npm run test --workspace=@locallink/api` (`vitest run`).

### Frontend (`apps/web`)

- `apps/web/src/features/auth/AuthContext.tsx` — the `AuthContext` object itself (previously only `AuthProvider`/`useAuth` were exported) and the `AuthContextValue` type are now exported, so tests can render `<AuthContext.Provider value={...}>` with a fixed, synchronous auth state instead of driving the real provider through HTTP/token/socket side effects.
- `apps/web/vitest.config.ts` + `apps/web/tests/setup.ts` — `jsdom` environment, `@vitejs/plugin-react` for JSX, `@testing-library/jest-dom` matchers, explicit `afterEach(cleanup)` (chosen `globals: false` over Vitest's global test functions, so every test file explicitly imports `describe`/`it`/`expect`/etc. — consistent with this codebase's general preference for explicit imports over ambient globals).
- `apps/web/tsconfig.vitest.json` — a third project reference alongside `tsconfig.app.json`/`tsconfig.node.json`, so `tests/` is actually type-checked. Necessary because of a real, previously-invisible bug this slice found: `apps/web`'s `typecheck` script was `tsc --noEmit`, but the root `tsconfig.json` is solution-style (`"files": []` + `"references"`) — and plain `tsc --noEmit` on a solution-style config silently checks **zero files** and exits 0, regardless of what's broken. Confirmed by deliberately introducing `const x: number = 'oops'` into `main.tsx`: `tsc --noEmit` reported nothing; `tsc -b` (which respects references) caught it immediately. `npm run build`'s `tsc -b && vite build` was accidentally the only thing that had ever actually type-checked this app — `npm run typecheck` had been a no-op since the solution-style config was introduced. Fixed by changing the script to `tsc -b`.
- `apps/web/tests/routing.test.tsx` (7 tests) — `RequireAuth`: renders `RouteLoadingFallback` while `isInitializing`, renders the outlet when authenticated, redirects to `/login` with `state.from` set to the attempted location when not, and — a direct regression guard for the redirect-flicker bug this component exists to prevent — never renders the login redirect while still loading even if the eventual auth state will be unauthenticated. `RequireRole`: renders the outlet for an allowed role, redirects home for a disallowed role, redirects home when there's no user at all.
- `apps/web/tests/customerCart.test.tsx` (2 tests) — mocks `features/customer/api.ts` and `lib/socket.ts`, renders the real `CustomerDashboard` with a fixed `AuthContext` value: adding a product from a different store than what's already in the cart surfaces the backend's `ApiError` message verbatim and leaves the cart's displayed total unchanged; adding another unit of a product already in the cart's store succeeds and shows the success message.
- 9 tests total, all passing; `npm run test --workspace=@locallink/web` (`vitest run`).
